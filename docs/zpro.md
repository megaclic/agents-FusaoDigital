# Z-PRO ("FusaoChatBot CRM") integration

A second, separate WhatsApp/CRM channel alongside the Chatwoot integration — a full vertical slice (Prisma models → public webhook receiver → normalize/mirror → agent runtime → admin + read REST → React pages → i18n) under `src/modules/zpro/*`. User-facing text calls it "FusaoChatBot CRM"; routes, table names (`zpro_*`), and internal identifiers keep the `zpro`/`Zpro` spelling — the rebrand is UI-only.

Independent of `src/modules/chatwoot/*` end to end: separate Prisma models, separate webhook mount, separate runtime (`runZproAgentTurn`, not `runAgentTurn`), separate checkpointer thread namespace. The two integrations never share code paths.

## Module map

- `types.ts` — raw webhook payload shapes (built from real captured payloads, 2026-08-06) + `NormalizedZproEvent`, the shape the runtime consumes.
- `constants.ts` — method/type-group literals, the agent gate flag name (`n8nStatus`), presence states, and the two in-memory TTLs (`ZPRO_IDEMPOTENCY_TTL_MS` for webhook dedup, `ZPRO_AGENT_ECHO_TTL_MS` for sender-type classification — see below).
- `parse.ts` — shared payload extraction (`extractMedia`, `extractMessageBody`, `extractWhatsappId`, `extractInstanceName`), used by both `normalize.ts` and `mirror.ts` so the two don't duplicate parsing.
- `normalize.ts` — `normalizeZproWebhook`: the **agent gate**. Returns `null` (drop) for non-message events, `fromMe` messages, groups, `botStopped`, `n8nStatus: false`, or an unresolvable channel identity. Only events that pass this gate reach `runZproAgentTurn`.
- `mirror.ts` — `mirrorZproMessage`: persists **every** message (client/agent/human), independent of the agent gate — the source of truth for `ZproConversationsPage`/`ZproConversationDetailPage`. Tolerates a concurrent-webhook-redelivery P2002 race on both the conversation and message upserts (see the file's own comments; covered by `tests/modules/zpro/mirror.test.ts`). Also exports `mirrorZproContact`: handles `contact-create-update` payloads, updating name/`avatarUrl`/number on every existing `ZproConversation` for that contact (no message is created). See "Contact identification" below.
- `agent-echo.ts` — `markAgentSending`/`wasAgentSending`: see "Sender-type classification" below.
- `stt.ts` — `resolveZproSttConfig`/`transcribeZproAudio`: audio transcription for the Z-PRO channel. See "Audio transcription (STT)" below.
- `vision.ts` — `resolveZproVisionConfig`/`extractZproFile`: image/document extraction for the Z-PRO channel. See "Vision (image/document extraction)" below.
- `tts.ts` — `sendZproVoiceReply`/`buildSetVoicePreferenceTool`: audio replies for the Z-PRO channel. See "Audio replies (TTS)" below.
- `guardrails.ts` — `makeZproGuardrailRunner`: input/output content moderation for the Z-PRO channel. See "Guardrails" below.
- `split.ts` — `deliverZproReply`: split + typing-paced delivery for text replies. See "Split + typing pacing" below.
- `tools.ts` — `loadZproAgentTools`: every tool source (RAG/HTTP/MCP/INTEGRATION + all NATIVE tools) granted to the agent bound to a Z-PRO instance. See "Tools" below.
- `native-tools.ts` — `buildZproNativeTools`: the Z-PRO-specific implementation of the 11 portable conversation-scoped NATIVE tools (handoff/note/attribute/contact-info/label/resolve/funnel-move/funnel-update/route-to-queue/schedule-message/skip), over `ZproClient` instead of Chatwoot's client. See "Native conversation tools" below.
- `crm.ts` — `readZproCrmConfig`/`resolveZproPipelineId`/`loadZproStages`/`loadZproTags`/`matchZproStage`: resolves the CRM Pipeline → Stage → Opportunity funnel context `kanban_move_card`/`update_kanban_task` operate on. See "CRM Pipeline funnel" below.
- `debounce.ts` — `resolveZproDebounceConfig`/`flushZproDebounceJob`/`parseZproThreadId`: inbound message-burst coalescing for the Z-PRO channel. See "Debounce" below.
- `nudge.ts` — `runZproAgentNudge`: proactive system-turn injection into an existing ticket (currently only Google Calendar appointment reminders). Reuses `runtime.ts`'s `runLoadedZproTurn` with a synthetic event, the same reuse `debounce.ts` already established. See "Proactive nudges (appointment reminders)" below.
- `runtime.ts` — `loadZproAgent` (resolves the bound agent + every per-agent config bag: model credential, guardrails, TTS, split, RAG maxDistance) + `runLoadedZproTurn` (the **shared turn tail**: build → invoke → recheck → post — guardrails, tools, `generate`, human-takeover recheck, TTS-or-text delivery) + `runZproAgentTurn` (the direct/webhook caller: CAS-claims the `ZproWebhookDelivery` row, calls `runLoadedZproTurn`, marks `PROCESSED`/`FAILED`). `flushZproDebounceJob` (`debounce.ts`) is the OTHER caller of `runLoadedZproTurn` — same split as Chatwoot's `runAgentTurn`/`runLoadedTurn`/the debounce flush.
- `analytics.ts` — `getZproFunnelMetrics`: current-state funnel counts (conversations/agent-handled/human-escalated/resolved) plus AI-usage totals (`promptTokens`/`completionTokens`/`calls`, from `LlmUsage.zproConversationId`) for the Dashboard's "FusaoChatBot CRM" section.
- `client.ts` — `ZproClient`, a ~90-method REST wrapper over the external Z-PRO v4 API (`{baseUrl}/v2/api/external/{apiId}/...`, Bearer auth). Most methods are unused today (built ahead of the UI that will call them); `listChannels()` backs the instance-modal probe (see below). See [`docs/zpro-api-reference.md`](zpro-api-reference.md) for the vendor's full API spec and the Google Calendar vs. Agendamentos distinction.
- `messages.ts` — reply-side helpers (`startTypingHeartbeat`, `sendTextReply` — a plain blank-line split with NO typing pacing, used for short administrative replies (the guardrail template/generated reply) — `sendMediaReply`, `saveContactMemory`). The MAIN reply's text path uses `split.ts`'s `deliverZproReply` instead (see "Split + typing pacing"); the audio path uses `tts.ts`'s `sendZproVoiceReply` (always `ZproClient.sendBase64` — see "Audio replies (TTS)" for why never `sendVoice`).
- `handoff.ts` — `activateAgent`/`deactivateAgent` (toggle `ticket.n8nStatus` via the external API), used by the manual toggle endpoint, the webhook's auto-handoff-on-human-intervention, AND (since this round) `native-tools.ts`'s `handoff_to_human`/`resolve_conversation` tools.
- `ctx.ts` — `sysCtx(tenantId)`: the canonical `TenantContext` for system-driven (non-request) DB access once the tenant is already known (webhook post-resolution, mirror, runtime). Contrast with `asSuperAdminOn`, used only pre-tenant-resolution in the webhook controller.
- `zpro-webhook-mount.ts` — the single global webhook path (`/api/v1/zpro/webhook`) and `zproWebhookUrl()` helper. Z-PRO has **one webhook per server**, not per-instance — no route token, unlike Chatwoot.

## Message flow

```
Z-PRO panel → POST /v1/zpro/webhook (public, no HMAC — Z-PRO doesn't sign)
  → resolve ZproInstance by whatsappId (tenant unknown yet → asSuperAdminOn, audited)
  → mirrorZproMessage (ALL messages, RLS-scoped once tenant is known)
  → mirrorZproContact (contact-create-update only — name/avatar refresh, best-effort)
  → eager STT (inbound voice notes — transcribe, write back to ZproMessage.body, re-broadcast)
  → eager vision (inbound image/document — describe/extract, write back to ZproMessage.body, re-broadcast)
  → auto-handoff: human sent this message while agent was still active → deactivateAgent, never re-activates automatically
  → handleZproWebhook (in-memory idempotency by messageId, TTL cache)
    → normalizeZproWebhook (agent gate)
    → ZproWebhookDelivery upsert (idempotency ledger, PENDING)
    → channel-redirect entry instance? → runZproRedirectGate (no AI — fixed reply + link to the
                                          Chatwoot widget; delivery marked PROCESSED, turn skipped)
    → debounce enabled? → armDebounce (re-arm the coalescing window; delivery marked PROCESSED, no turn yet)
                         : runZproAgentTurn — detached, ack already sent (<5s)
```

**Direct path**: `runZproAgentTurn` CAS-claims the delivery row, resolves the bound agent (`loadZproAgent` — model credential, guardrails, TTS, split, RAG threshold configs), and calls the shared turn tail `runLoadedZproTurn` (build → invoke → recheck → post; thread `zpro:<tenantId>:<zproInstanceId>:<ticketId>` — its own checkpointer namespace, never collides with a Chatwoot thread), then marks the delivery `PROCESSED` or `FAILED`. A `turnId` is generated once in the controller (before the STT/vision steps) and threaded through to the turn, so a voice note's `stt` (or an image's `vision`) flowlog stage and the turn's own stages (`generate`, `tts`, `split`) land on the same `/logs` row.

**Debounce path** (see "Debounce" below): the fast worker flushes the coalesced burst straight from `ZproMessage` (no re-fetch) and calls the SAME `runLoadedZproTurn`, so both paths get identical guardrails/tools/TTS/split behavior — only how the burst's text is assembled, and how "am I still allowed to post" is decided, differs.

## Sender-type classification (`ZproSenderType`: CLIENT | AGENT | HUMAN)

`mirror.ts`'s `resolveSenderType` used to trust `ticket.userId` (the ticket's **assigned** attendant — sticky, set once and never cleared) as a proxy for "who authored this message." That is wrong: once any ticket has a human assignee, every later AI-sent message was misclassified `HUMAN` — confirmed against real data (`{{nome_contato}}`-containing, unmistakably AI-generated replies stored as `HUMAN`).

Fix: `runLoadedZproTurn` (`runtime.ts`) calls `markAgentSending(zproInstanceId, ticketId)` right before sending the reply. `mirror.ts` checks `wasAgentSending(...)` **first** when classifying a `fromMe` message — if true, it's `AGENT` regardless of `ticket.userId`; otherwise it falls back to the `ticket.userId` heuristic (genuinely means HUMAN in that case, since we're the only source of AGENT-authored messages — human replies always come from the Z-PRO panel, never through our code). A false HUMAN classification is NOT just a mislabel: `zpro.controller.ts`'s auto-handoff-on-human-intervention gate reacts to it by calling `deactivateAgent` — the agent goes silent, requiring a manual `POST /v1/zpro/conversations/:id/toggle-agent` to recover.

The marker is **DB-backed** (`ZproConversation.agentSendingUntil`, short-TTL via `ZPRO_AGENT_ECHO_TTL_MS`, 2min) — covers multi-balloon replies + webhook round-trip lag + a slow turn (guardrails/RAG/tool calls) ahead of the send, expires on its own by timestamp comparison, no "unmark" needed. **Went through two in-memory attempts first, both failed live the same day (2026-08-14)**: a plain module-level `Map` (wiped by any `bun --hot` reload — reruns the module on every edit to a file it transitively imports, which during active development is constantly); then a `globalThis`-singleton `Map` (survives hot-reload, but not a full process restart) — the false-HUMAN/auto-deactivate sequence recurred a THIRD time even with that fix live, strongly suggesting a process restart (not just a reload) landed between a mark and its echo. A DB column survives both failure modes, at the cost of one extra round-trip per send/classification — negligible next to the other DB calls already on that path. Production (no `--hot`, one stable process) was never actually at risk from either in-memory failure mode; this hardening is a direct response to how disruptive it was during THIS session's live local-dev testing.

## Template variables

The system prompt is interpolated via the same canonical, sanitized resolver the Chatwoot path uses (`src/graph/prompt.ts`: `buildPromptVars` + `interpolatePromptVars`, called from `prepare.ts` for Chatwoot) — `runLoadedZproTurn` calls it directly before building the graph, AFTER `composeSystemPrompt` appends the grounding directive when the agent was granted `search_knowledge` (see "Tools" below — same `grounded` mechanism Chatwoot uses). Resolves `{{nome_contato}}`/`{{primeiro_nome}}` (from `ticket.contact.name`), `{{telefone_contato}}` (`ticket.contact.number`), `{{canal}}` (`ev.channelType`), `{{nome_empresa}}` (`Tenant.name`), `{{nome_agente}}` (`Agent.name`), plus all the time variables (`{{hora_atual}}`, `{{data_atual}}`, …). `{{canal}}` renders blank on the debounce flush path (`ZproConversation` doesn't store the channel type) — a minor, accepted degradation, see "Known, accepted gaps".

## Contact identification (name + avatar)

`ticket.contact.profilePicUrl` arrives on the Z-PRO `contact-create-update` webhook method (a separate payload shape from `message`, gated by `ZPRO_METHOD_CONTACT` in `constants.ts`). `mirrorZproContact` (`mirror.ts`) handles it: `updateMany` on every `ZproConversation` matching `(zproInstanceId, contactId)`, refreshing `contactName`/`contactNumber`/`avatarUrl` — no message is created, and it no-ops (zero rows affected, no error) if the contact has no conversation yet. Called from `zpro.controller.ts` right after `mirrorZproMessage`, wrapped in try/catch (best-effort, never blocks the webhook ack).

**OPEN-VALIDATION**: only the `message` method's payload shape has a real captured sample (`types.ts`, 2026-08-06); `contact-create-update` carrying `whatsapp.id` at the payload root (needed to resolve the instance before `mirrorZproContact` ever runs) is assumed, not confirmed. If a real capture shows otherwise, `extractWhatsappId` will reject the payload earlier (`outcome: "skipped:no-whatsapp-id"`) and this code path never executes — no crash, just silent no-op. Confirm against a live payload and tighten once available.

`avatarUrl` is a plain nullable column on `ZproConversation` (and, for the Chatwoot side, on `Contact` — populated from `sender.thumbnail` in `normalize.ts`/`mirror.ts`). The frontend never renders the raw external URL directly (CSP `img-src` only allows same-origin/data/blob) — both `GET /v1/conversations/:id/avatar` and `GET /v1/zpro/conversations/:id/avatar` proxy it through `assertSafeOutboundUrl` (anti-SSRF) + a plain `fetch`, same pattern as the existing Chatwoot attachment proxy. The shared `<Avatar>` component (`src/client/components/Avatar.tsx`) hits these endpoints and falls back to initials on load failure.

## Audio transcription (STT)

Mirrors the Chatwoot "eager STT at message arrival" pattern (`docs/stt.md`): transcription runs in the webhook controller (`zpro.controller.ts`, step "1c"), independent of the agent gate, so a human operator sees the transcript even on turns the agent gate would otherwise drop (`n8nStatus: false`, `botStopped`, etc.) — and independent of whether an agent is even bound to the instance.

- **Config resolution**: `resolveZproSttConfig(tenantId, zproInstanceId, base)` (`stt.ts`) resolves the bound agent via `ZproAgentBinding` (not `Inbox.agentId` — Z-PRO has no inbox concept) then reads the same generic `agent.settings.stt` schema Chatwoot uses (`readSttConfig`, `src/modules/stt/settings.ts`). Same Behavior-tab UI, no Z-PRO-specific config surface.
- **Download + decrypt**: unlike Chatwoot (which downloads via an authenticated `ChatwootClient` call), Z-PRO's webhook payload carries the raw WhatsApp CDN URL (`message.audioMessage.url`, e.g. `https://mmg.whatsapp.net/...`) directly — `transcribeZproAudio` downloads it with `assertSafeOutboundUrl` (anti-SSRF: blocks private/loopback/CGNAT ranges, forces HTTPS) before an injectable `fetchImpl` runs. **That blob is WhatsApp's own end-to-end-encrypted media, not plain audio** — confirmed live (2026-08-14) that `audioMessage.mediaKey` arrives on every voice note. **`mediaKey`'s wire shape is UNCONFIRMED and already changed once**: the WhatsApp protocol calls for base64, but the live capture showed a plain array-like object instead (`{"0":n,"1":n,...,"31":n}` — a Buffer/Uint8Array serialized without its `.toJSON()`, losing its array-ness over the wire) — `parse.ts`'s `parseMediaKey` normalizes both shapes (plus a real byte array, for good measure) to base64 before anything touches it, same defensive posture as `parseContactTags`. `media-crypto.ts`'s `decryptWhatsappMedia` then unwraps it (HKDF-SHA256, no salt, info `"WhatsApp Audio Keys"`, expands the 32-byte key into iv/cipherKey/macKey; the download is `ciphertext || hmac-sha256[0:10]`, MAC-verified before AES-256-CBC decrypt — protocol shared with Baileys/whatsapp-web.js, not a Z-PRO-specific scheme) before the plaintext is handed to the provider (`getSttProvider`, `src/modules/stt/providers.ts`) and cleaned with `cleanTranscription` (`chatwoot/render.ts`, shared — the Amara.org Whisper hallucination filter isn't Chatwoot-specific). `mediaKey` is optional on `transcribeZproAudio`'s params (defensive — a payload shape without it falls back to feeding the downloaded bytes as-is, matching pre-decryption behavior, rather than refusing outright). A MAC/decrypt failure is treated exactly like a download failure (logged, `null`, never a thrown exception) — it never falls back to feeding still-encrypted bytes to the provider.
- **Persistence — write-back target differs from Chatwoot**: Chatwoot writes the transcript back to Chatwoot itself (the source of truth there). Z-PRO's inbox UI is sourced from `ZproMessage` (`mirrorZproMessage` already wrote the message with an empty `body` when the voice note first arrived), so the controller updates that same row's `body` in place (keyed by `conversationId_messageId`) and re-broadcasts over the realtime channel so an operator already viewing the conversation sees the transcript land live.
- **Feeds the agent turn**: the transcribed text is also stuffed into the normalized event's `body` right before dispatch (`if (sttText && !event.body) event.body = sttText`) — a voice note with no caption would otherwise have empty `text` in `runtime.ts` and be skipped (`outcome: "skipped"`) before ever reaching the graph.
- **Best-effort, never blocks**: no STT configured, no credential, download failure, decryption failure (bad key / corrupted download), or provider error all resolve to `null` — the voice note stays mirrored with an empty body (today's pre-STT behavior), logged via `emitFlowEvent`/`withFlowStage` with `stage: "stt"` (a minimal `FlowContext` is built in the controller specifically for this, since `runtime.ts`'s own `FlowContext` doesn't exist yet at this point in the request).
- **KNOWN GAP — silent drop on empty text, not STT-specific**: when transcription (or vision, below) yields nothing, both `runZproAgentTurn`'s direct path and `debounce.ts`'s `flushZproDebounceJob` treat the resulting empty `text` as "nothing to reply to" and silently mark the delivery processed / advance the watermark — **no fallback message is sent to the customer**, and no `/logs` line beyond the buried `stt`/`vision` `status:"error"` row signals it happened. Before this decryption fix, EVERY voice note hit this path (100% silent-drop rate); now it's the rarer case of a genuine STT/vision hiccup (provider outage, quota, corrupted download) — but the mechanism itself is unfixed. A customer who sends a voice note during a provider outage still gets no reply and no visible error. Flagged, not yet fixed.

## Audio replies (TTS)

Reuses the Chatwoot-shared TTS stack end to end (`docs/tts.md`: the provider registry, `readTtsConfig`/`shouldReplyWithAudio`, `synthesizeReply`) — zero Chatwoot coupling in any of it. `runLoadedZproTurn` (`runtime.ts`) wires it into the reply-modality decision right after the graph produces a reply, mirroring `src/graph/runtime.ts`'s own audio-vs-text branch:

- **Config**: `agent.settings.tts` is the same generic per-agent bag Chatwoot reads (`readTtsConfig`) — `loadZproAgent` also returns `ttsConfig`, so the Behavior tab's TTS section needs no Z-PRO-specific change to apply to a Z-PRO-bound agent (same precedent as STT/vision/tools).
- **Format is always Ogg/Opus (or mp3 for openrouter)**: Z-PRO is WhatsApp-only — there's no Instagram-style channel split like Chatwoot's `pickTtsFormat(provider, channelType)`, so `runLoadedZproTurn` always calls `synthesizeReply` with `channelType: null`, which already resolves to the WhatsApp-first default.
- **Sending — `tts.ts`'s `sendZproVoiceReply`, ALWAYS through `ZproClient.sendBase64` (the generic `/base64` file endpoint), never `ZproClient.sendVoice` (`POST /voice`).** Used to branch on the synthesized mime (Ogg/Opus → `sendVoice`, everything else → `sendBase64`) on the assumption `sendVoice`'s `audio` field accepted base64 — **confirmed WRONG live (2026-08-14)**: the vendor's own Postman example documents that field as a PUBLIC URL to an already-hosted file, not inline data. Calling it with base64 returns 200 (no request-shape validation) but the voice note silently never reaches WhatsApp — every stage of our own pipeline logged success, `generate`→`tts`→the send itself all "ok", yet nothing arrived; only the raw dev-server stdout trace (not `/logs`) proved the send call itself had completed without throwing. Since we synthesize audio in-memory with no hosting/upload step to produce a URL, `/voice` is unusable for us — `sendBase64` is used unconditionally now, for every format. **Trade-off**: the reply lands as a downloadable file attachment, not a native playable voice-note bubble (no waveform/PTT rendering) — worse fidelity, but it actually arrives. `messages.ts`'s unused `sendVoiceReply` helper (dead code with the identical bug, zero callers) was deleted rather than fixed in place.
- **Per-contact preference — `ZproConversation.voiceReply`, not `Contact.voiceReply`**: Z-PRO has no `Contact` table (same trade-off as `tools.ts`'s `contactDbId` — see "Tools" below), so the preference lives on `ZproConversation` instead. Set by `tts.ts`'s `buildSetVoicePreferenceTool`, a Z-PRO-specific equivalent of Chatwoot's native `set_voice_preference` tool (`src/graph/tools/native.ts`) that writes here instead. Z-PRO has no NATIVE tool-grant UI for conversation tools (see "Tools" below), so this ONE tool is wired directly in `runLoadedZproTurn` — appended to the tool list only when `ttsConfig.mode === "preference"` (no point exposing a preference-setting tool when the mode can never honor it) and a `ZproConversation.id` is known. The value is re-read AFTER the graph invoke (not the pre-invoke snapshot used for the tool's description) so a preference the model just set governs the SAME reply.
- **Best-effort, never blocks**: any synthesis error, or `synthesizeReply` returning `null` (unconfigured/misconfigured provider), falls back to the existing text path, which runs unconditionally after the audio branch — a TTS failure never drops the reply. The `tts` flow-log stage is spanned via the same `FlowContext` as `generate` (see "AI usage capture" below for the correlation pattern).

## Vision (image/document extraction)

Mirrors "Audio transcription (STT)" above, and Chatwoot's own eager-vision pattern (`src/modules/vision/service.ts`) — reuses the SAME generic provider registry (`getVisionProvider`, `visionKindForMime`, `readVisionConfig`) with zero Chatwoot coupling. Runs in the webhook controller (`zpro.controller.ts`, step "1d"), independent of the agent gate, right alongside STT — a message is audio XOR image/document (`extractMedia` already treats the two as mutually exclusive), so at most one of the two blocks runs per message.

- **Config**: `resolveZproVisionConfig(tenantId, zproInstanceId, base)` (`vision.ts`) resolves the bound agent via `ZproAgentBinding`, then `readVisionConfig` on `agent.settings.vision` — same Behavior-tab UI as Chatwoot, no Z-PRO-specific surface.
- **Download + decrypt**: the raw WhatsApp CDN URL from the payload (`imageMessage.url`/`documentMessage.url`), through `assertSafeOutboundUrl` (anti-SSRF) — not Chatwoot's authenticated `client.downloadAttachment`. Same encrypted-CDN reality as STT above: `extractZproFile` decrypts via `media-crypto.ts`'s `decryptWhatsappMedia` before classifying/extracting anything, keyed by the ORIGINAL WhatsApp message type (`"image"` or `"document"` — not the vision `kind` computed below, which can disagree: an image sent "as document" is still HKDF-keyed as `"WhatsApp Document Keys"`). `mediaKey`/`mediaType` are optional (defensive fallback to pre-decryption behavior); a decrypt failure resolves to `null`, same contract as a download failure.
- **Kind classification is off the DOWNLOADED content-type when it disagrees, EXCEPT after a successful decrypt** — the CDN's Content-Type header describes the *encrypted* transport (typically generic, e.g. `application/octet-stream`), not the plaintext, so once decryption succeeds the payload's own `mediaMimetype` is trusted instead. Pre-decryption (no `mediaKey`, the legacy/defensive path), the downloaded content-type still wins, mirroring Chatwoot's own re-derivation. An unsupported kind (e.g. `image/svg+xml`) or a PDF on an image-only provider (`supportsDocuments: false`) skips cleanly, logged `stage: "vision", status: "skipped"`.
- **Persistence and turn-feeding**: identical contract to STT — the extracted text overwrites `ZproMessage.body` in place (`conversationId_messageId`), re-broadcasts over realtime, and is fed into the normalized event's `body` before dispatch (`if (visionText && !event.body) event.body = visionText`) so an image/document with no caption still reaches the graph.
- **Best-effort, never blocks**: no vision configured, no credential, download failure, decryption failure, unsupported mime, or provider error all resolve to `null` — the message stays mirrored with an empty body (pre-vision behavior), logged via `stage: "vision"`. Same silent-drop gap as STT above applies here too.

## Guardrails (input/output moderation)

Reuses the fully generic guardrails engine end to end (`src/modules/guardrails/{analyze,settings}.ts` — `analyzeGuardrail`, `readGuardrailsConfig`, both zero-Chatwoot-coupling) via `guardrails.ts`'s `makeZproGuardrailRunner`, the ONLY Z-PRO-specific piece being the trip note (`ZproClient.createNote` in place of Chatwoot's `client.sendPrivateNote`).

- **Config + credential**: `loadZproAgent` resolves `agent.settings.guardrails` (`readGuardrailsConfig`) and, when enabled, the guardrails agent's OWN separate model credential (fail-open + logged if unresolvable) — identical structure to the main model credential resolution just above it in the same function, and to `src/graph/prepare.ts`'s Chatwoot equivalent.
- **Wiring**: `runLoadedZproTurn` builds the guardrails model once, then runs the INPUT check on the customer's text before the graph invoke (a violation posts the configured template/generated reply — through the SAME `shouldPost` supersede gate the main reply uses — or stays silent), and the OUTPUT check on the model's reply before delivery (a violation replaces the reply or suppresses the send). Exactly mirrors `src/graph/runtime.ts`'s two guardrail checkpoints.
- **Before this port, Z-PRO conversations had ZERO content moderation** — this was the highest-priority item in the Chatwoot-vs-Z-PRO gap analysis that motivated this round of work (a real risk exposure, not a missing feature).

## AI usage capture (LlmUsage / Dashboard "LLM usage")

`runLoadedZproTurn` passes a `UsageCapture` (`src/graph/usage.ts`, the same LangChain callback Chatwoot uses) into `graph.invoke({ ... }, { callbacks: [usageCapture] })` — shared by both the direct and debounce paths (see "Message flow"). The row it writes uses a **dedicated `LlmUsage.zproConversationId` column**, never `LlmUsage.conversationId` — `Conversation.id` (Chatwoot) and `ZproConversation.id` (Z-PRO) are independent autoincrement sequences with no FK on either usage column, so reusing one for the other risks silently attributing a Z-PRO turn's tokens to an unrelated Chatwoot conversation of the same numeric id (or vice versa). `inboxId` is always `null` for Z-PRO rows (no inbox concept), which already correctly excludes them from `getInstanceMetrics`'s `byInbox` breakdown.

Because the Dashboard's aggregate "LLM usage" totals/`byAgent`/`byModel`/`bySource` (`getInstanceMetrics`, `src/modules/analytics/service.ts`) sum over `LlmUsage` without filtering by `conversationId`, Z-PRO usage is included there automatically — no extra wiring needed once the callback is attached. The Dashboard's top "Automation funnel" (`getKpis`) and the daily chart's per-conversation denominator (`getTimeseries`) are **deliberately left Chatwoot-only** — both feed a cost-per-conversation ratio sourced from Langfuse, which has no Z-PRO tracing (see "Known, accepted gaps" below); folding Z-PRO conversations into that denominator without matching cost in the numerator would silently understate the figure. Z-PRO's own AI-usage totals are surfaced instead by `getZproFunnelMetrics` (`promptTokens`/`completionTokens`/`calls`, "real" `source: "inbox"` only — same convention as `getKpis`), shown as a "Tokens (in / out)" card in the Dashboard's "FusaoChatBot CRM" section. See the comment above `getKpis` in `src/modules/analytics/service.ts` for the full reasoning.

## Dashboard funnel

`GET /v1/zpro/conversations/analytics/funnel?since=<ISO>` (`zpro-conversations.controller.ts`, `requireAuth`) → `getZproFunnelMetrics`: `conversations`/`agentHandled`/`humanEscalated`/`resolved` counts on `ZproConversation` within the window, plus `promptTokens`/`completionTokens`/`calls` summed from `LlmUsage.zproConversationId` (see "AI usage capture" above). **The conversation-state counts reflect current state, not history** — `ZproConversation` has no audit trail, so a conversation that was agent-handled and later escalated only counts toward `humanEscalated`, never both. The Dashboard's "FusaoChatBot CRM" section (`DashboardPage.tsx`) only renders for tenants with at least one `ZproInstance` — resolved once via `GET /v1/zpro/instances`, independent of the date-range control.

## Instance setup: channel probe

`POST /v1/zpro/probe` (`zpro-admin.controller.ts`, `TENANT_ADMIN`, no DB access) tests `{baseUrl, apiId, bearerToken}` against the external API's `listChannels()` and returns `{ok, channels: [{id, name, type, status}]}` — never a 500, any failure or unusable shape returns `{ok: false, channels: []}`. The add-instance modal (`ZproSection.tsx`) is two-phase: enter credentials → probe → pick a channel (auto-resolves `whatsappId`, previously a manually-typed number). A "enter manually instead" escape hatch preserves the original single-phase flow if the probe doesn't work against some deployment.

**Open-validation**: `listChannels()`'s response shape has no captured real-payload sample (unlike the webhook payloads, which come from a real capture) — the mapper in `zpro-admin.controller.ts` is deliberately defensive (tries a few plausible shapes, coerces/defaults fields, drops unusable items). Confirm against a live Z-PRO instance and tighten once available.

## Tools (INTEGRATION, RAG, HTTP, MCP, NATIVE)

An agent bound to a Z-PRO instance can be granted RAG (knowledge-base search), HTTP (operator-defined tools), MCP servers, INTEGRATION (Google Calendar, Asaas, ...), and NATIVE conversation tools the exact same way a Chatwoot agent can — same grant UI (`ToolGrantsEditor.tsx`; channel-agnostic except the tools each channel hides when the other side's binding is missing, `react_to_message`/`route_to_queue`/`get_contact_info` — see "Native conversation tools") and the same underlying assembly: `runLoadedZproTurn` calls `tools.ts`'s `loadZproAgentTools`, which runs `loadToolSelections` (`src/graph/tools/assemble.ts`, the SAME function Chatwoot uses — it already resolves all 5 grant sources in one scoped read) and then, OUTSIDE that transaction, builds each source with its own generic, zero-Chatwoot-coupling builder: `buildToolpackTools` (INTEGRATION), `buildRagTools` (RAG), `buildHttpTools` (HTTP), `loadMcpToolsForAgent` (MCP — the only one that does network I/O, an MCP `connect()` call, hence built after the tx closes), `buildNativeTools` (the 2 utility tools) + `buildZproNativeTools` (the 11 conversation tools — see "Native conversation tools" below). `grounded` (`search_knowledge` granted) feeds `composeSystemPrompt` exactly like Chatwoot (see "Template variables").

**Before this port, `loadZproAgentTools`'s predecessor only read `integrationSelections` from `loadToolSelections`'s return and silently discarded `ragConfig`/`httpToolDefs`/`mcpSelections`/`nativeToolsAllow`** — an operator granting RAG/HTTP/MCP/NATIVE to a Z-PRO-bound agent via the (channel-agnostic) grant UI saw the grant "save" with zero runtime effect. This is now resolved: all 5 sources are read and built.

- **2 utility NATIVE tools, always on when granted — `calculator`/`get_current_time`**: built via `buildNativeTools(ctx, utilityNativeAllow(selections.nativeToolsAllow))` with a duck-typed `client: {} as ChatwootClient` (neither tool ever touches `ctx.client`) — the EXACT pattern the playground already uses for context-free tools (`src/modules/playground/service.ts`).
- **`set_voice_preference` is handled separately, not through either native chain**: Chatwoot's native version hard-codes a write to `Contact.voiceReply`; Z-PRO's equivalent (`tts.ts`'s `buildSetVoicePreferenceTool`, writing `ZproConversation.voiceReply`) is wired directly in `runLoadedZproTurn` instead — see "Audio replies (TTS)".
- **`contactDbId`/RAG `threadId` stamp**: toolpacks/RAG that isolate per-customer data (Calendar's `secv4Contact` ownership stamp; RAG's per-thread suggestion tracking) need a `ZproConversation.id`-shaped stamp. Z-PRO has no `Contact` table (see the schema comment above `ZproConversation`); `tools.ts` uses `ZproConversation.id` instead — correct isolation per ticket, but a phone number that opens a new ticket later gets a new id and "loses" visibility into appointments/suggestions stamped under the old one. Acceptable for now; revisit if Z-PRO ever gets a stable per-phone-number contact.
- **Toolpacks that need a live Chatwoot handle will fail gracefully, not run**: `ToolpackCtx.chatwoot` (client + conversationId) is never populated for Z-PRO — Google Drive's `send_file` requires it and will error out if granted to a Z-PRO agent (the tool wrapper never throws uncaught, so this is a clear tool-error message to the model, not a crash). Google Calendar and Asaas don't touch `ctx.chatwoot` at all and work as-is.
- **No allowlist by catalogType/tool source**: any RAG/HTTP/MCP/INTEGRATION/NATIVE granted to a Z-PRO agent is exposed — the grant itself (an explicit operator action) is the security boundary, same philosophy as Chatwoot.

## Native conversation tools

Chatwoot's implementations of the 13 conversation-scoped NATIVE tools (`src/graph/tools/native.ts`) are ALL hard-typed to `ChatwootClient` — Chatwoot Pro kanban board/step/task, Chatwoot's own labels, Chatwoot's custom-attribute definitions, Chatwoot agents/teams. None of that infrastructure exists for Z-PRO, so `native-tools.ts`'s `buildZproNativeTools` is a PARALLEL implementation over `ZproClient`, mapped onto Z-PRO's own primitives, built inside `loadZproAgentTools` only when a live `client` is passed in (always true from `runLoadedZproTurn`; tests exercising only RAG/HTTP/MCP/INTEGRATION may omit it and get none). Chatwoot implements 11 of the 13 (missing `route_to_queue` and `get_contact_info`, both Z-PRO-only BY DESIGN, not just unimplemented — see their rows below); Z-PRO implements 12 of the 13 (missing only `react_to_message`, no Z-PRO reaction API). `ToolGrantsEditor.tsx` hides each channel's gaps from its grant grid (`channelBinding.chatwoot`/`channelBinding.zpro`) instead of leaving a silently-inert grant visible:

**Data mapping: queue, tags, contact memory.** `ticket.queueId` and `ticket.contact.tags`/`.extraInfo` arrive on EVERY message webhook (confirmed on real captured payloads) but used to be received and discarded entirely — `route_to_queue`/`assign_label` could only WRITE, with no way for either the agent or the operator to see what a ticket/contact already had. Fixed:

- `ZproConversation.queueId` (`Int?`) and `.contactTags` (`Json`, an array of `{id,name}` pairs — `contact.tags`'s shape is UNCONFIRMED, so `mirror.ts`'s `parseContactTags` keeps whichever half of id/name each entry actually has and degrades to `[]` on any other shape) are now mirrored on every `mirrorZproMessage`/`mirrorZproContact` write. `contact.extraInfo` is NOT persisted (no schema change needed): it's threaded straight from `NormalizedZproEvent.extraInfo` (already extracted by `normalize.ts`, previously extracted and never read by anything) through `LoadZproAgentToolsParams.contactExtraInfo`.
- `crm.ts`'s `resolveQueueName`/`resolveContactTagNames` turn the mirrored id/name pairs into display strings against the SAME cached `loadZproQueues`/`loadZproTags` catalogs `route_to_queue`/`assign_label` already load (`tools.ts` extends `needsQueues`/`needsTags` to trigger for `get_contact_info` too — no extra network round trip for it specifically). An id with no catalog match (a deleted/renamed queue, a stale tag) falls back to `"tag #<id>"` rather than silently dropping it.
- The conversation detail page (`ZproConversationDetailPage.tsx`) shows the resolved queue name + tag badges in the header — resolved server-side in `zpro-conversations.controller.ts`'s `GET /conversations/:id` (the only endpoint that resolves them; the list endpoint doesn't, to avoid a catalog lookup per row).

**Commitment discipline guardrail.** Two live incidents (a "send this in 5 minutes" request and a Google Calendar reminder) showed the model confirming a delayed action in prose WITHOUT calling any tool — twice, once even where a real tool (Calendar) already existed. `src/graph/prompt.ts`'s `composeSystemPrompt` now always appends a `COMMITMENT_DIRECTIVE` (unlike `GROUNDING_DIRECTIVE`, not gated on a tool grant): never promise a future action without calling the backing tool in the same response, and say so plainly when no such tool exists. Applies to BOTH channels (the same `composeSystemPrompt` call in `prepare.ts` and `runtime.ts`) — a behavioral backstop, not a substitute for `schedule_message` existing.

**`handoff_to_human` never supports Chatwoot's `pinned`/`agent_choice` targeting.** `agent.settings.handoff.targetAgentId`/`targetTeamId` are Chatwoot **user/team ids** — applying them to a Z-PRO ticket's `userId` would silently assign the WRONG person, the same class of cross-system id collision risk already avoided for `LlmUsage.zproConversationId` (see "AI usage capture"). The Z-PRO handoff tool always behaves like Chatwoot's `"route"` mode (deactivate the agent, leave the ticket's queue/assignment untouched) regardless of the configured mode. A Z-PRO `listUsers` + a dedicated target picker is plausible future work, not attempted here.

**Operator guidance** (`agent.settings.toolGuidance`, `agent.settings.handoff.instructions` for handoff's summary toggle) is the SAME generic bag Chatwoot writes — a dual-bound agent's guidance text applies to both channels' tool descriptions. The funnel guidance for `kanban_move_card` is the ONE exception: it lives in its own `agent.settings.zproCrm.instructions` key (see below), independently namespaced from Chatwoot's `agent.settings.kanban.instructions`, so a dual-channel agent can carry different funnel guidance per channel if ever needed.

**Playground**: `native-tools.ts`'s `buildSimulatedZproNativeTools` (wraps the 11 tools above, plus `set_voice_preference`, in the same `simulatedTool` no-op used by Chatwoot's `buildSimulatedNativeTools`) is what a Z-PRO-bound agent's **Playground** tab actually exercises — `src/modules/playground/service.ts`'s `resolvePlaygroundChannel` picks this builder over Chatwoot's when the tested agent is bound to a `ZproInstance` and not to a Chatwoot `Inbox`. Before this, the playground unconditionally simulated the Chatwoot flavor for every agent, so testing a Z-PRO-only agent showed Chatwoot-shaped handoff/kanban behavior (and let `react_to_message` appear to work) — see `docs/playground.md`.

## CRM Pipeline funnel (`kanban_move_card` / `update_kanban_task`)

Z-PRO has two candidate concepts for "kanban," neither a 1:1 match for Chatwoot Pro's per-conversation card (board + step + title/description/priority/dates):

- A simple per-**CONTACT** "kanban carteira" (`updateContactKanban(contactId, kanbanId)`) — one flat column assignment, no card metadata, no per-conversation granularity.
- The **CRM Pipeline → Stage → Opportunity** funnel (`pipeline/*`, `stage/*`, `*Opportunity` endpoints) — a real sales funnel with card-like fields (name/value/status/responsible/closing-forecast/description).

`kanban_move_card`/`update_kanban_task` use the CRM Pipeline funnel — the only Z-PRO concept with card-like fields, chosen over the simpler "carteira" deliberately (confirmed with the operator before implementing, since it's a real product/UX decision, not an implementation detail).

- **No per-id GET for an Opportunity** in the external API (only Create/Update/Delete/List, and `listOpportunities` doesn't filter by contact/ticket) — so unlike Chatwoot's `loadKanbanContext` (one live `GET` per turn), the "current stage" here is **OUR OWN mirror**: `ZproConversation.opportunityId`/`opportunityPipelineId`/`opportunityStageId`/`opportunityStageName`/`opportunityTitle`, refreshed on every successful `kanban_move_card`/`update_kanban_task` write. Best-effort — it can drift if the deal is edited directly in the Z-PRO panel; there is no reconciliation job.
- **The linked Opportunity is created LAZILY on first tool use in a conversation** — Z-PRO, unlike Chatwoot (where the operator attaches an existing card via the Chatwoot UI), has no such "link a card to this conversation" step on our side. The first successful `kanban_move_card` or `update_kanban_task` call in a ticket calls `createOpportunity` (seeded from the contact's name/number) and persists the returned id; every later call in that same ticket calls `updateOpportunity` instead.
- **`updateOpportunity` requires `name` on EVERY call** (no partial-field PATCH for it in the vendor API) — `opportunityTitle` is persisted specifically so a plain stage move (`kanban_move_card`, which never touches the title) always resends the LAST KNOWN title instead of accidentally reverting a title the model set via `update_kanban_task`.
- **Which Pipeline**: `agent.settings.zproCrm.pipelineId` (`crm.ts`'s `readZproCrmConfig`). When unset, `resolveZproPipelineId` **auto-detects the tenant's sole pipeline** (a live `listPipelines()` call, 60s TTL cache) — zero-config for the common single-pipeline case. Zero or 2+ pipelines with no explicit id is ambiguous: both tools report "no CRM pipeline is configured" instead of guessing. **No dedicated UI picker exists yet** — a multi-pipeline tenant sets it via `PATCH /v1/agents/:id` (`{"settings":{"zproCrm":{"pipelineId":16}}}`, the REST settings bag is already a free-form passthrough) or MCP is not yet wired for this one key (`src/modules/agents/behavior-settings.ts`'s allowlist doesn't include `zproCrm`) — a known, accepted gap given the auto-detect path covers most tenants.
- **`update_kanban_task`'s field set is Z-PRO's own, not a forced Chatwoot mapping**: `title`/`description`/`value`/`status` (`open`/`win`/`lose`)/`closingForecast`. There is no `priority` field on a Z-PRO Opportunity at all (omitted, not faked) and no `startDate` either (only `closingForecast`, the expected close date).
- **Response shapes are UNCONFIRMED**: the vendor's Postman collection ships no example responses for `pipeline/list`/`stage/list`/`listTags`/`createOpportunity`. Every parser in `crm.ts`/`native-tools.ts` is defensive (accepts a bare array or a common wrapper key like `{data:[]}`, tries a few plausible id fields on a create response) and degrades to an empty list / a clear tool-level error rather than throwing. Confirm against a live Z-PRO instance and tighten once available.

## Split + typing pacing

Reuses the fully generic pure helpers (`src/modules/split/service.ts`'s `splitReply`/`typingDelayMs`/`readSplitConfig`/`SplitConfig` — the SAME ones Chatwoot uses) via `split.ts`'s `deliverZproReply`, but NOT Chatwoot's `deliverReply` itself (hard-coded to `ChatwootClient.sendMessage`/`toggleTyping`). `deliverZproReply` is the Z-PRO equivalent over `ZproClient.sendText` for the split/pacing shape — called by `runLoadedZproTurn` for the MAIN reply (not the guardrail template/generated reply, which uses `messages.ts`'s simpler `sendTextReply` with no pacing — mirrors Chatwoot's own guardrail send going through the raw `client.sendMessage`, not `deliverReply`, either). Unlike Chatwoot's `deliverReply`, it does **not** toggle presence itself — see the heartbeat below.

Config (`agent.settings.split`) is the same generic bag `readSplitConfig` reads for Chatwoot — enabled by default, `maxChars`/`typingWpm`/`min`+`maxDelayMs`/`maxChunks`, same Behavior-tab UI.

**"Digitando..." heartbeat, for the WHOLE turn, not just delivery.** WhatsApp's own "composing" presence chatstate is NOT persistent — a client reverts it well before a naive refresh interval suggests. `runLoadedZproTurn` used to send a single one-shot `sendPresence("typing")` at turn start (`messages.ts`'s old `sendTyping`), and `deliverZproReply` used to send another single one-shot signal per balloon, right before sleeping up to `maxDelayMs` (8s default) before actually sending it — both flickered on then off well before the next real event (the LLM finishing, or the balloon actually going out), the reported "aparece e some" symptom. Live testing against an Evolution API-relayed instance showed the visible bubble timing out closer to 1-2s than the originally-assumed ~4s. Fixed by centralizing presence in ONE place: `messages.ts`'s `startTypingHeartbeat(client, ticketId)` fires "typing" immediately, then again every 1.5s, for the ENTIRE turn — started right after the client is built in `runLoadedZproTurn`, stopped (sending one "paused") in an outer `try/finally` wrapping the rest of the function so it clears on every exit path (posted/blocked/taken-over/superseded/empty/thrown). Since this is the ONLY caller of `deliverZproReply`, the per-balloon signal in `split.ts` was redundant (and buggy in the same way) — removed, not just re-timed. The flicker complaint recurred even after the interval tighten, with no way to tell whether a tick was silently failing or silently slow — `startTypingHeartbeat` now optionally logs every tick (`stage: "presence"` in `src/modules/flowlog/stages.ts`, `ok`/`error` + `durationMs`) when called with a `flow` context (as `runLoadedZproTurn` does), so a future recurrence is diagnosable from `/logs` instead of guessing at a fourth interval value.

**No read-receipt (blue checkmarks) equivalent — genuine API gap, not a bug.** The external Z-PRO API exposes `sendPresence` (typing/paused) but NO endpoint to mark a message as read (confirmed against the full vendor Postman collection — same class of gap as `react_to_message`'s missing reaction endpoint). There is nothing our side can call to make WhatsApp show a read confirmation on the customer's side.

## Debounce (inbound message coalescing)

WhatsApp customers send several quick balloons ("oi", "tudo bem?", "queria saber…"); debounce waits for the customer to stop, then answers the whole burst in one turn — same n8n-parity feature as Chatwoot's (`docs/debounce.md`), reusing its infra almost entirely:

- **Same `SchedulerJob` kind ("DEBOUNCE"), same fast worker, same arm mechanics**: `armDebounce` (`src/modules/debounce/service.ts`) has ZERO Chatwoot coupling — it only bookkeeps `threadId`/a JSON payload via an upserted, advisory-locked `SchedulerJob` row — so Z-PRO reuses it AS-IS (`agentBotId: null`, meaningless for this channel but harmlessly passed through). `debounceFlushHandler` (`src/modules/debounce/handler.ts`, the ONE function registered for kind `"DEBOUNCE"`) branches by threadId shape: `zpro:<tenantId>:<instanceId>:<ticketId>` → `zpro/debounce.ts`'s `flushZproDebounceJob`; Chatwoot's `tenantId:instanceId:conversationId` (3 parts, no `zpro` segment) → the existing `flushDebounceJob`, unchanged. **No scheduler-side change was needed** to add the second channel — same fast-drain cadence, same anti-starvation ceiling, for both.
- **The flush itself is SIMPLER than Chatwoot's**: Chatwoot's flush must re-fetch the conversation from the live API (admin token) because the anti-PII rule forbids mirroring message bodies locally. Z-PRO has no such rule — `mirrorZproMessage` already writes `ZproMessage.body` as the inbox's source of truth — so `flushZproDebounceJob` coalesces DIRECTLY from the local DB (`ZproMessage.findMany({senderType: "CLIENT", id: {gt: watermark}})`), zero network re-fetch.
- **Watermark**: `ZproConversation.lastHandledMessageId` (`BigInt?`, our OWN `ZproMessage.id` — not an external id like Chatwoot's `Int`, so no int/bigint conversion at the boundary), advanced by the same monotonic CAS pattern as `advanceHandledWatermark` (`{lastHandledMessageId: null} OR {lt: target}` → update; a losing concurrent writer sees 0 rows). Gate-closed (human took over between arm and flush): advances from the payload's `lastMessageId` (set at arm time from `mirrorZproMessage`'s new `messageDbId` return) with NO query, mirrors Chatwoot's issue-#8 fix verbatim.
- **`shouldPost`** (passed into `runLoadedZproTurn`): re-checks for any newer CLIENT message past the target watermark (supersede — a message arrived mid-turn, drop this reply, the re-armed flush answers the full burst) and, if none, performs the watermark CAS. The SAME callback covers every posting exit in `runLoadedZproTurn` (the guardrail-template reply AND the main reply) — one check, like Chatwoot's.
- **Human-takeover recheck**: after the graph invoke, `runLoadedZproTurn` re-reads `ZproConversation.agentActive` — if a human took over WHILE the LLM call was running, the reply is dropped (`"taken-over"`) instead of posted. Direct analog of Chatwoot's `shouldBotHandle`/assignee recheck, keyed on the same flag the auto-handoff step (see "Message flow") flips.
- **Synthetic event for the coalesced burst**: `flushZproDebounceJob` builds a `NormalizedZproEvent` from `ZproConversation`'s own columns (`contactName`/`contactNumber`) since there's no live webhook payload to read from — `channelType` is left blank (unavailable outside a real payload), a minor `{{canal}}` degradation only (see "Template variables").
- **Testing note**: `runLoadedZproTurn` calls `createChatModel` directly (no injectable `deps`, unlike Chatwoot's `runLoadedTurn`) — `tests/modules/zpro/debounce.test.ts` covers the watermark/gate/supersede DATA logic (the actual correctness-critical surface) up to but not through a real graph invoke; no Z-PRO test in this codebase exercises the live LLM path end-to-end.

## Channel redirect (WhatsApp → website chat)

Z-PRO can be a redirect **entry point** too, landing on the SAME Chatwoot web widget as the Chatwoot-native flow (`docs/channel-redirect.md`) — one lead-conversion feature, two possible entry channels. `agent.settings.channelRedirect.entryZproInstanceId` (a `ZproInstance.id`, independent of `entryInboxId`) gates it; the Redirect tab's "Z-PRO entry instance" picker lists the tenant's instances bound to the edited agent.

- **Wired in `zpro.controller.ts`'s dispatch callback**, right after the STT/vision merge and before the debounce-arm block — a consumed outcome (`"sent"`/`"silent"`) marks the `ZproWebhookDelivery` `PROCESSED` and returns, so the message never reaches debounce or `runZproAgentTurn`; `"misconfigured"` (feature off, or provisioning incomplete) falls through to the normal flow so the lead is still served on WhatsApp.
- **The one real difference from the Chatwoot-native gate: identity.** A Chatwoot WhatsApp lead already has a `chatwootContactId` — Chatwoot itself auto-creates the contact on the first inbound message, before our webhook even runs. A Z-PRO lead never touches Chatwoot at all, so `runZproRedirectGate` (`src/modules/channel-redirect/gate.ts`) creates the Chatwoot contact itself on first redirect, via a new `ChatwootClient.createContact` (the standard Contacts API, not fork-specific), then stamps the `fzwa:<id>` identifier and mints the token exactly like the Chatwoot-native path (`resolveRedirectLink`, reused verbatim). The created contact's id is persisted on `ZproConversation.redirectChatwootContactId` so a resend reuses the SAME Chatwoot contact instead of creating a new one every time. **OPEN-VALIDATION**: `createContact`'s response shape is unconfirmed against a live instance (defensive parsing, several plausible shapes tried) — confirm and tighten once available.
- **Watermarks**: `ZproConversation.redirectSentAt`/`redirectCount` mirror `Conversation`'s columns exactly (same `shouldSendRedirect` one-shot + cooldown logic, reused verbatim).
- **The follow-up ladder (`src/modules/channel-redirect/followup.ts`) is NOT ported** — it already runs entirely on the widget-side conversation (Chatwoot), so it fires identically regardless of which channel originated the redirect; nothing Z-PRO-specific was needed there.

## Proactive nudges (appointment reminders)

`src/graph/nudge.ts`'s `runAgentNudge` (used by several callers — see `docs/graph.md`) is Chatwoot-only by construction (it parses a `tenantId:instanceId:conversationId` thread and talks to `ChatwootClient`). Z-PRO's Google Calendar appointment reminders (`src/modules/appointments/reminders.ts`) were the first proactive-nudge caller ported (below); the generic inactivity follow-up sweep and the channel-redirect follow-up ladder were ported later (Fase 6, see "Known, accepted gaps"). Appointment reminders: a Z-PRO agent could already book/list/update/cancel/confirm calendar events (Calendar's tools never touched `ctx.chatwoot`), but the reminder-arming closures (`scheduleAppointmentReminders`/`cancelAppointmentReminders`) were never wired into `tools.ts`'s `ToolpackCtx` — so no `APPOINTMENT_REMINDER` scheduler job was ever enqueued, and even if one had been, `appointmentReminderHandler`'s `parseThreadId` would have rejected the Z-PRO thread shape and silently marked the job `"done"`. Both are now fixed:

- **`tools.ts`** now wires `scheduleAppointmentReminders`/`cancelAppointmentReminders` into the toolpack ctx, using the same channel-agnostic `enqueueAppointmentReminders`/`cancelAppointmentReminders` (`src/modules/appointments/reminders.ts`) Chatwoot uses — keyed by the already-`zpro:`-prefixed `threadId`, so no new thread-shape handling was needed there.
- **`appointmentReminderHandler`** now dispatches by thread shape (`threadId.startsWith("zpro:")`, mirrors `debounce/handler.ts`'s `debounceFlushHandler` branch) to a NEW `nudge.ts`'s `runZproAgentNudge` instead of `runAgentNudge`.
- **`runZproAgentNudge` reuses `runtime.ts`'s `runLoadedZproTurn`** with a synthetic `NormalizedZproEvent` — the SAME reuse `debounce.ts`'s `flushZproDebounceJob` already established for a non-webhook `text`. This is a deliberate departure from Chatwoot's nudge (which builds its own minimal model/graph, skipping guardrails/tools/split/TTS): a reminder's "ask for confirmation" step needs real tool-calling (`calendar_confirm_appointment`) to work, and `runLoadedZproTurn` already provides it for free. Trade-off accepted: the nudge text also passes through the INPUT guardrail (harmless for the fixed nudge templates — `renderNudge`'s fenced-data wrapping already treats embedded fields as semi-trusted, so this is an extra safety margin, not a regression).
- **Service-window/HSM gate (Fase 6)**: `runZproAgentNudge` now passes `proactive: { lastInboundAt }` to `runLoadedZproTurn`, which gates the send through `proactiveSendMode` exactly like the generic follow-up sweep does (see "Known, accepted gaps") — freeform inside the window (still the default for every instance, since `isOfficialWaba` defaults `false`), an approved template or an explained private note outside it on a flagged instance. If a human owns the conversation (`ZproConversation.agentActive === false`) when the reminder fires, `runZproAgentNudge` skips it entirely rather than trying to post a private note (Chatwoot's behavior) — a human already being engaged makes an automated attendance reminder redundant, not missing.
- **`postActions` (label/resolve)**: `runZproAgentNudge` itself still has no `postActions` param (this caller doesn't need it) — the generic follow-up sweep applies its own `assignLabels`/`resolve` directly in `followups/handlers.ts`'s Z-PRO branch instead, via a small `ZproClient` helper, not through `runZproAgentNudge`.
- **`calendar_create_event`'s business-hours availability check is now wired for Z-PRO too**: `resolveBusinessHoursById` (`src/graph/prepare.ts`, exported — the SAME function Chatwoot's `buildToolset` binds) is bound into `tools.ts`'s `ToolpackCtx.resolveBusinessHours`, so a Z-PRO agent's Calendar `check_availability`/`create_event` now honors a configured `BusinessHours` schedule exactly like Chatwoot. This is our OWN per-agent `BusinessHours` model (`/resources/business-hours`, referenced by an integration selection's `config.businessHoursId`) — unrelated to Z-PRO's own per-queue "Horário de Atendimento" (configured in the Z-PRO admin panel under Filas), which is not exposed by the external API (`createQueueData`/`updateQueueData` only carry `queue`/`isActive`) and governs Z-PRO's own ticket routing, not our Calendar tool.

## Known, accepted gaps

- **`emitFlowEvent`/`withFlowStage`**: `"stt"`/`"vision"` (controller, eager extraction), `"generate"`/`"tts"`/`"split"`/`"handoff"`/`"debounce"` (`runtime.ts`/`debounce.ts`) are spanned; tool calls aren't (`ToolFlowLogger` is Chatwoot-only) — a tool call succeeding or failing today leaves no line in `/logs`.
- **No Langfuse tracing**: `runLoadedZproTurn` builds the model/graph directly, never calls `buildCallbacks`/`buildLangfuseHandler` — no trace is emitted for Z-PRO turns (including tool calls) even when Langfuse is configured for the tenant. This is also why the Dashboard's cost-per-conversation figure stays Chatwoot-only (see "AI usage capture" above) — there is no Z-PRO cost to attribute.
- ~~No `lastInboundAt` / service-window / generic follow-ups~~ **RESOLVED (2026-08-13)**: `ZproConversation` now has `lastInboundAt`/`lastFollowUpAt` (advanced in `mirror.ts` on CLIENT messages). The generic inactivity follow-up sweep (`agent.settings.followUp`) now also sweeps `zpro_conversations` (`src/modules/followups/handlers.ts`, dispatch by thread-id shape) and calls `runZproAgentNudge` — same episode/business-hours/appointment-suppression/redirect-exclusion gates as Chatwoot, plus deterministic `assignLabels`/`resolve` post-actions over `ZproClient`. The WhatsApp 24h window/HSM gate is also wired: `ZproInstance.isOfficialWaba` (manual toggle, default `false` — **not auto-detected**, see "Instance setup: channel probe" above for why) feeds the same `proactiveSendMode` Chatwoot uses; outside the window on a flagged instance, `runLoadedZproTurn` sends an approved template (`ZproClient.sendTemplateWABABody`, new `sendZproTemplate` helper — **OPEN-VALIDATION**: the `components` shape is the Meta Cloud API standard, never confirmed against a live WABA-connected Z-PRO instance) or an explained private note. The channel-redirect follow-up ladder's Z-PRO resend (`sendWhatsAppFollowUp`/`deliverRedirectClosing` in `src/modules/channel-redirect/followup.ts`) is gated the same way. The debounce watermark (`lastHandledMessageId`) remains a DIFFERENT column with a different purpose (reactive coalescing, not proactive re-engagement).
- **A Z-PRO channel-redirect's created Chatwoot contact can drift** — `ZproConversation.redirectChatwootContactId` is a point-in-time snapshot (set once, on first redirect); if that Chatwoot contact is later merged/deleted directly in Chatwoot, a resend would target a stale id. No reconciliation exists (same class of accepted drift as the CRM Opportunity mirror below).
- **`ZproWebhookDelivery.FAILED` is terminal**: `attempts` increments but nothing retries a failed delivery (no reaper exists for either integration, not zpro-specific). Debounce-armed deliveries are marked `PROCESSED` immediately at arm time (the reply is tracked by the watermark from then on, not this ledger).
- **`react_to_message` has no Z-PRO API equivalent** — confirmed against the full vendor Postman collection (not just `client.ts`'s wrapped subset): no message-reaction endpoint exists in the external API at all. Never built for Z-PRO turns; see "Native conversation tools".
- **`handoff_to_human`'s `pinned`/`agent_choice` targeting is Chatwoot-only** — Z-PRO's handoff always behaves like `"route"` (see "Native conversation tools" for why: the configured target ids are Chatwoot user/team ids, a cross-system collision risk to apply directly). No `listUsers`/queue-targeting picker exists yet.
- **`agent.settings.zproCrm.pipelineId` has no dedicated UI picker or MCP surface** — REST-only (`PATCH /v1/agents/:id`) for the multi-pipeline case; the common single-pipeline case needs no config at all (auto-detected). See "CRM Pipeline funnel".
- **The CRM Opportunity "current stage" can drift from the Z-PRO panel** — no per-id GET exists in the external API to reconcile against; see "CRM Pipeline funnel".
